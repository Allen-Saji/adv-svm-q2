Solana Architecture: End-to-End

Every component, in the order a transaction touches them. Read once linearly to absorb the sequence, then come back to each section as reference. Block-building infrastructure plugs in at one specific point on this map; the goal is to see exactly where.

Slot: 400 ms Validators: ~2,000 State: ~1.5 TB Read time: ~20 min

00The 10,000-ft Map

Every box below appears later as its own section. Hold this picture in your head while reading.

Solana in one frame. Everything below this point is a zoom-in on one of these boxes.

01Client Side: Tx Construction

Before the network sees anything, a lot of structure is already baked into the transaction.

  1. User picks an action in a frontend. Frontend assembles a tx: list of instructions, each = program + accounts + data.
  2. Fetch a recent blockhash from any RPC. Expires after ~150 slots. Doubles as replay protection + soft state binding.
  3. Serialize instructions, accounts (with writable + signer flags), blockhash, fee payer.
  4. Sign with Ed25519. Whole tx must fit in 1232 bytes (single MTU after IPv6 overhead).
  5. Send to an RPC node via sendTransaction JSON-RPC. The tx leaves the user's machine.
★ Insight

The 1232-byte ceiling is exactly why Address Lookup Tables (ALTs) exist -- they let you reference up to 256 accounts with 1-byte indices instead of 32-byte pubkeys. Every modern Solana protocol uses ALTs because the size budget is the real-world constraint, not compute.

02Gulf Stream: Forwarding to the Leader

Solana skips the mempool. Txs go straight to whoever's holding the mic.

  1. RPC looks up the leader schedule -- every node knows current + upcoming leaders (computed once per epoch from previous epoch's stake).
  2. Forward via QUIC to current leader. Gulf Stream = speculative forwarding before the leader's slot even begins.
  3. Near slot boundary: forward to next leader too. Hides handoff latency -- next leader buffers incoming txs while predecessor finishes.
  4. SWQoS gates ingress. 80% of TPU bandwidth reserved for staked-node connections. Unstaked RPCs frequently lose connection slots under load.
No mempool. Direct forwarding to current + next leader. The 4-slot window amortizes handoff cost.

03Inside the Leader: The TPU Pipeline

This is where every Solana block-building company fights for influence.

5 stages. Each is its own thread (Agave) or tile (Firedancer). Banking does the actual work; everything else is plumbing.

Fetch + SigVerify

  1. 3 QUIC sockets: tpu (user) · tpu_vote (votes) · tpu_forwards (overflow).
  2. 100k packet buffer total. SWQoS enforced at the connection layer.
  3. Signatures verified -- Ed25519 SIMD-parallel. Firedancer can FPGA-accelerate to 8M sigs/sec.
  4. Dedup vs the recent blockhash window kills replays.
  5. Failed-sig txs get a discard flag -- pipeline keeps moving; downstream stages skip them.

Banking Stage (block building lives here)

  1. Central scheduler thread pulls high-priority txs into a look-ahead window. (Default since Agave 2.3.)
  2. Builds a prio-graph -- edges connect each tx to its next-highest-priority conflict per writable account.
  3. Per tx: check live lock map → if conflict, park behind a dep edge → else dispatch to one of 4 worker threads → mark accounts locked.
  4. Worker executes via SVM -- load accounts → walk instructions → CPI as needed → track CU → commit atomic.
  5. On done: release locks, prio-graph re-evaluates downstream waiters.

PoH + Broadcast

  1. Successful tx hashes → PohRecorder.
  2. Mixed into the SHA-256 chain: hash[n+1] = SHA256(hash[n] || tx_hash).
  3. 64 ticks per slot, every ~6.25ms. PoH doesn't wait -- late txs miss the block.
  4. Entries = hash + conflict-free txs, signed by the leader.
  5. Packed into ~1200-byte shreds. 32 data + 32 coding = any 32 reconstruct.
  6. Merkle-chained, leader-signed. First shred's signature anchors the whole block.
  7. Handed to Turbine for propagation.
★ Insight

The PoH thread decides when the slot ends. Banking does its best to fill before the 64th tick. If your tx misses the leader's 1.6-second window, it's gone -- Solana has no carry-over. Resubmit. This is the structural opposite of Ethereum's persistent mempool.

04Turbine: Block Propagation

How shreds reach every other validator in ~100-200ms.

Turbine. Fanout-200 multi-hop tree. ShredStream (Jito) skips this for whitelisted searchers -- direct shred delivery from the leader.
  1. Stake-weighted shred-deterministic tree. Per-shred pseudorandom seed shapes the tree.
  2. Fanout ~200 per node. Higher stake → closer to root.
  3. 2-3 hops to full cluster. 100-200ms typical; Agave 3.1 shipped 200* faster Turbine via XDP.
  4. Jito ShredStream bypasses the tree for whitelisted UDP subscribers -- saves hundreds of ms.

05Every Other Validator: The TVU

~99.97% of the time you're not the leader. You're verifying their work.

  1. Shred Fetch receives shreds from Turbine.
  2. Shred Verify checks Merkle root, leader signature, FEC reconstruction.
  3. Repair Protocol kicks in for gaps -- gossip request: "missing shreds 47-52 of slot N." Peers respond.
  4. Block assembly reconstructs entries from shreds.
  5. ReplayStage re-executes every tx against local state in PoH order. This is what makes Solana deterministic -- every honest node arrives at the same state.
  6. Bank fork updated for the parent slot's bank.
★ Insight

Every non-leader re-executes every transaction. This is one of Solana's biggest CPU costs and exactly what APE removes -- under APE the block is a pure ordering commitment, not an execution receipt, so consensus stops requiring redundant re-execution. Huge validator-cost win whenever it lands.

06Voting & Consensus (TowerBFT)

How a block goes from "shipped" to "irreversible."

TowerBFT's lockout-doubling. The economic cost of reversing a vote grows exponentially as you stack more votes on the same fork.
  1. Validator replays a block → constructs a vote tx: "I, validator X, vote for slot N on fork F."
  2. Vote tx sent via tpu_vote socket (or gossip). It's a regular tx -- pays fees, lands in a future block.
  3. Vote Program records it in the validator's vote account (a tower of recent votes + lockouts).
  4. Lockout doubles on each consecutive same-fork vote. 32 votes deep = 2^32 slots = effectively permanent.
  5. Fork choice = heaviest sub-tree. Validators always vote on the branch with most cumulative stake.
  6. Optimistic confirm at >2/3 stake. Rollback would slash >1/3.
  7. Rooted (finalized) after 32 subsequent slots with >2/3 stake voting on top of slot N.
  8. Switch proof needed to fork: 38% stake on an alternative your previous fork can't catch (33% + 4.66% buffer).
★ Insight

Vote txs consume ~75% of Solana ledger bandwidth today. Alpenglow's Votor moves votes off-chain via BLS aggregation -- that single change shrinks the ledger ~75% and enables 100-150ms finality. It's the biggest throughput win on the roadmap.

07Gossip Protocol always on

The cluster-wide chat that handles everything shreds can't.

  1. Push messages -- contact info, recent votes, snapshot hash, stake info -- broadcast periodically.
  2. Pull responses for catch-up after a node falls behind.
  3. Push graph self-balances -- each node picks a small random peer set per round.
  4. Bloom filters dedupe traffic so the same vote isn't rebroadcast endlessly.
  5. Repair requests ride this channel -- "send me shreds 47-52 of slot N."

08AccountsDB & State Persistence

The ~1.5TB append-only state database that every executed tx writes to.

  1. Every executed tx → AccountsDB. Massive append-only store.
  2. AppendVec -- memory-mapped files holding successive account versions.
  3. State partitioned by slot. Current Bank tracks deltas on top of previous slot's state.
  4. Cleanup / shrink runs periodically. Old account versions in AppendVecs get pruned + compacted.
  5. Snapshots every ~100 slots -- frozen rooted state, tar'd, used by new validators to bootstrap without genesis replay.
  6. AccountsHash -- every account's data + metadata Merkle-hashed into the BankHash. This is what consensus actually agrees on.

09The SVM Runtime

How programs actually execute. The "Sealevel" parallel engine.

Why Solana parallelizes: every tx pre-declares its account access. The scheduler reasons about conflicts before executing anything.
  1. Program = BPF binary stored in an account marked executable. Written in Rust/C.
  2. SVM loads tx accounts -- writable accounts cloned, read-only borrowed.
  3. Walks each instruction: looks up target program → invokes BPF entry → passes data + account context.
  4. CPI lets programs call other programs mid-execution. Stack depth limit: 4.
  5. CU tracked per instruction. Default 200k/tx, max 1.4M/tx. Block: 60M. Per writable account: 12M.
  6. PDAs -- accounts owned by programs, derived from seeds. No private key.
  7. Sysvars hold cluster state (clock, rent, blockhashes) readable by programs.
  8. State writes commit only if entire tx succeeds. Any instruction failure → atomic rollback.
★ Insight

The declarative account access model is the entire reason Sealevel works. Ethereum can't trivially parallelize because you only learn what state a tx touched after executing it. Solana txs ship with their full access list -- the scheduler can build conflict-free batches before anything runs. This is the single architectural choice that defines Solana's parallelism story.

10Epoch & Stake Lifecycle

The long-running loop that defines who leads what slot.

  1. Epoch boundary every ~432,000 slots (~2 days). At each boundary: stake activates (delegated last epoch), deactivates (cooldown), inflation rewards distribute, leader schedule for next epoch computes from current stake state.
  2. Validators register a vote account + identity account when joining. Vote account has commission %.
  3. Stakers delegate by creating a stake account pointing at a vote account. JitoSOL etc. abstract this into liquid wrappers.
  4. Leader selection = stake-weighted pseudorandom over the epoch, granting 4-consecutive-slot windows. 2% stake → ~2% of slots in 4-slot chunks.

11Where the MEV Stack Plugs In

Everything from earlier conversations, located precisely on the sequence above.

  1. Jito-Solana = Agave fork adding RelayerStage (200ms hold, pseudo-mempool), BlockEngineStage (gRPC to central auction), BundleStage (atomic bundle execution before Banking).
  2. Bundles = ≤5 txs, atomic, same-slot. Include transfer to one of 8 tip PDAs.
  3. TipRouter NCN distributes tips at epoch boundary -- 3% to Jito DAO/NCN, 97% to validator + stakers per MEV commission.
  4. Harmonic = sidecar (harmonic/proposer) alongside Agave. When validator is leader: receives candidate blocks from N independent builders via Harmonic engine, applies configured policy, selects winner. Falls back to local build if engine fails.
  5. Searchers submit bundles to Jito's block engine AND Harmonic's whitelisted endpoint. Real-time DEX / mempool / lending monitoring; race for inclusion.

12The Roadmap (What Changes)

The roadmap. Alpenglow lands first and is the biggest near-term win. APE is the structural break that reshapes block building permanently.
  1. Alpenglow (Q3 2026): Tower BFT → Votor (BLS, 100-150ms finality). Turbine → Rotor (single-hop, Phase 2). PoH-as-clock → fixed 400ms intervals.
  2. Firedancer continues maturing. Frankendancer ~26% stake. Full Firedancer ~5% and growing. Provides true client diversity + deterministic latency.
  3. Constellation (late 2026 - 2027): 16 Proposers + 256 Attesters on 50ms cycles. Pslices attested by ≥40% MUST be included = protocol-enforced censorship resistance.
  4. APE (2027+): consensus and execution decoupled. Block becomes pure ordering commit. UserBlockSlots = formal builder role.
  5. ACE (2027+): contracts dictate their own tx sequencing. Protocols enforce FIFO or app-defined ordering at the protocol layer.

13The Loop in One Picture

Every Solana slot is one full instance of this loop in 400ms. Block-building overlays live entirely on the leader; consensus + replay run on everyone.

14The Three-Layer Frame

If you only carry one mental model from this whole document, it's this one.

LayerWhat it doesWhat lives here
NetworkMove bytes between nodesGulf Stream · Turbine · Gossip · Repair · Shreds
ConsensusDecide which fork is canonical & when slots become irreversibleTowerBFT (today) · Votor (Alpenglow)
ExecutionCompute stateTPU · TVU · ReplayStage · SVM · AccountsDB

The block-building wars (Jito, Harmonic, BAM, Paladin) all live entirely inside the execution layer, specifically inside the leader's TPU. They don't touch consensus. They don't change the network layer. They just influence what Banking decides to schedule.

This is why APE is so disruptive: it's the first proposal to break consensus and execution apart, moving the block-building battlefield from "an in-process integration with the leader" to "a formal protocol role with its own slots and signatures." Everything Harmonic is building is a pre-position for that world.

The leader runs everything in 400ms. Every other component of Solana exists either (a) to feed the leader transactions, (b) to verify the leader's output, or (c) to influence what the leader decides to schedule.
★ Where block building fits

All block-construction work happens in one window of this sequence: between step 14 (tx leaves SigVerify) and step 23 (entry handed to broadcast). Everything else is unchanged. Anything labelled "block building" that falls outside that window is doing something different.
