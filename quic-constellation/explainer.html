Monday · async self-studyQUIC: the transport layer for transactions

QUIC is a UDP-based, multiplexed, always-encrypted transport. It folds the TLS 1.3 handshake into the transport handshake, gives each logical message its own stream so one lost packet does not stall everything behind it, and identifies connections by a Connection ID rather than the IP/port 4-tuple. Solana adopted it for transaction ingest because the handshake gives the validator a cryptographic identity per client, which is the hook that stake-weighted prioritization hangs on.

RFC 9000 §4 - Flow control: a credit system

QUIC flow control is a limit-based credit scheme. The receiver advertises the maximum total number of bytes it is willing to accept, and the sender must never exceed it. There are two independent levels, and the binding constraint is whichever you hit first:

  • Stream level - MAX_STREAM_DATA bounds bytes on one stream. Initial value comes from a transport parameter; the receiver raises it later with a MAX_STREAM_DATA frame.
  • Connection level - MAX_DATA bounds the sum of bytes across all streams. Raised with a MAX_DATA frame.
  • Concurrency (a separate axis, §4.6) - MAX_STREAMS bounds how many streams a peer may open, not how many bytes. This is the lever Agave actually uses to throttle.
The credit model. A sender may only transmit up to the advertised limit. When it runs out it is "blocked" and may send a DATA_BLOCKED / STREAM_DATA_BLOCKED frame as a hint. Crucially, the receiver MUST NOT wait for that hint before raising the limit, or the sender could stall forever.

The §4.1 rules that matter (this is the AI "Explain" exercise)

  • A receiver advertises a limit; senders MUST NOT exceed either the stream or the connection limit.
  • A receiver MUST close the connection with FLOW_CONTROL_ERROR if a sender sends past an advertised limit.
  • Limits are monotonic in effect: advertising a smaller limit is legal but has no effect, and a sender ignores any frame that does not increase a limit.
  • Blocked-state frames (DATA_BLOCKED, STREAM_DATA_BLOCKED, STREAMS_BLOCKED) are SHOULD-level debugging signals only.
  • Throughput is capped by flow control if the window is smaller than the bandwidth-delay product (BDP = bandwidth × RTT).

RFC 9000 §17 - Packet formats

The most significant bit of byte 0 selects the header form: 1 = long header (used before 1-RTT keys exist), 0 = short header (used once the handshake is up). There is exactly one short-header packet type in QUIC v1: the 1-RTT packet.

Easy thing to get wrong

The Retry packet has no packet number field and cannot be acknowledged. A first-pass reading often assumes every long-header packet has a packet number - Retry does not. Anti-amplification (§9.3) is why it exists: before validating the client's address, a server must not send more than 3x the bytes it received.

RFC 9001 - TLS 1.3 is not layered on top, it cooperates

In TCP+TLS, TLS records sit inside TCP as a separate layer. In QUIC, TLS hands its record-layer job to QUIC: handshake messages travel directly in QUIC CRYPTO frames, and TLS pushes packet-protection keys down to QUIC as each encryption level becomes available.

  • Header protection (§5.4): a separately derived key encrypts the packet-number field and the low bits of byte 0. This is the headline difference from TCP+TLS, where sequence numbers are fully visible to any on-path observer.
  • Key derivation uses TLS 1.3 HKDF-Expand-Label with QUIC-specific labels ("quic key", "quic iv", "quic hp") for cryptographic domain separation from TLS itself.
  • 0-RTT replay (§9.2): early data is replay-exposed exactly as TLS early data is. QUIC's transport state is idempotent, so the risk lives in the application protocol. "Disabling 0-RTT entirely is the most effective defense."

The sans-I/O split in Quinn (quinn-proto does no I/O, just state transitions) is the key design idea to internalize: it makes the protocol logic deterministic and testable, and embeddable in any event loop. s2n-quic's distinguishing bet is formal verification and aggressive fuzzing rather than API ergonomics.

Tuesday · liveMCPs - Multiple Concurrent Proposers

Today's topic is the single-leader problem and the design space that tries to fix it. On Solana today, one leader per slot has a monopoly over which transactions get in and in what order. That monopoly is the root of two things the protocol would rather not have: censorship (a leader can simply drop your transaction) and MEV extraction (a leader can reorder, sandwich, and front-run).

What "Multiple Concurrent Proposers" means

MCP breaks block construction away from the single leader. Instead of one node deciding content, several proposers build transaction batches concurrently, and the leader's job shrinks to assembling those batches under tight constraints. The leader keeps liveness and ordering of the final block; the proposers collectively own what gets included. The design goal is order fairness: a transaction that enough proposers saw must make it into the block.

The single-leader failure modes

  • Selective censorship - the leader drops specific transactions at zero cost.
  • MEV - reorder, insert, sandwich for profit.
  • Liveness coupling - one slow or offline leader stalls inclusion for everyone in that slot.

What MCP changes

  • Many proposers run at once, rotated by stake.
  • Inclusion becomes a protocol rule, not a leader's discretion.
  • Hiding the batch contents until inclusion neutralizes content-based MEV.
The foundational paper

"Multiple Concurrent Proposers: Why and How" - Garimidi, Neu (a16z Crypto Research) and Max Resnick (Anza), 2025, arXiv:2509.23984. It is described as the only MCP design in the current literature that formally achieves both selective-censorship resistance and hiding simultaneously. Constellation (Wednesday) is the concrete Solana instantiation, and Resnick (Thursday) is a co-author. Reading the abstract and introduction before Tuesday will pay off.

Wednesday · liveConstellation as an Alpenglow preprocessor

Constellation is Anza's concrete Multiple Concurrent Proposers proposal (authors: Brennan Watt and Max Resnick). It does not replace Alpenglow - it runs in front of it. The division of labor is the single most important sentence this week: Alpenglow provides safety and liveness; Constellation provides order fairness. The batches Constellation produces become the payload of Alpenglow's blocks.

Alpenglow recap (the thing Constellation feeds)

Votor - voting / finalization

  • Fast path: 1 round, ≥80% stake, target ~100ms.
  • Slow path: 2 rounds, ≥60% stake each, target ~150ms.
  • Both run concurrently; block finalizes when the faster path completes.
  • Uses BLS signature aggregation; replaces TowerBFT + PoH-based voting.

Rotor - dissemination

  • Single-hop relay layer replacing Turbine's multi-layer tree.
  • Leader erasure-codes the block (Reed-Solomon) into shreds; relays each broadcast their portion to all.
  • Relays sampled by stake; bandwidth used proportional to stake.
  • Only a subset of shreds is needed to reconstruct.
Resilience & latency

Alpenglow targets ~100-150ms finality (down ~100x from TowerBFT's 12.8s) and a 20+20 fault model: up to 20% Byzantine stake plus an additional 20% crashed/offline stake, so 40% non-responsive tolerance while staying under 33% Byzantine.

The pshred lifecycle, proposer to leader

This is Wednesday's headline mechanic. Each cycle, a proposer turns its accepted transactions into a pslice, erasure-codes it into 256 pshreds (the "p" is silent, to distinguish from Alpenglow's slices), and sends one pshred to each of 256 attesters. Every pshred carries a hash commitment to the full ordered transaction list, so the leader cannot reorder or substitute after attesters have signed.

Proposer to leader. The hash commitment in each pshred is the anti-tamper hook; the attestation record is the anti-censorship hook. Steps 5-6 hand off into Alpenglow.

The three thresholds - do not confuse them

64 / 256
Recovery threshold (25%). Any 64 of 256 pshreds reconstruct the pslice. This is the "Constellation whitepaper's recovery threshold" the lab validates against.
40%
Inclusion threshold. A pslice attested by ≥40% of attesters must be in the block, or the block is invalid.
60%
Validity threshold. Block-level validity; below it, the slot is skipped.
"Constellation-parameterised encoder" = HECC

Constellation's north star is a Hiding Erasure-Correcting Code (HECC): parameterized so any T shreds reveal no information about the batch, while K + T shreds allow full reconstruction - information-theoretic hiding on top of erasure recovery, which is what kills content-based MEV. Important nuance: the shipped v1 uses plain Reed-Solomon (like Turbine) with only partial hiding; full HECC is deferred. So "Constellation-parameterised encoder" means an erasure encoder tuned to HECC's (T, K) thresholds, which v1 approximates. The formal treatment is in arXiv:2509.23984.

The 50ms tick budget - latency per round

Constellation's fundamental time unit is a 50ms cycle, billed by Anza as the fastest protocol-enforced economic tick of any production blockchain. Everything a proposer does - assemble the pslice, Reed-Solomon encode it into 256 pshreds, and distribute one to each attester - must fit inside that 50ms. This is exactly why FEC overhead has to be quantified against the budget: encoding plus dissemination plus attestation cannot overrun the window.

Illustrative budget split (proportions are schematic, not Anza-published). The constraint is real: the entire encode-and-disseminate path must complete inside one 50ms cycle. For reference, Alpenglow's Rotor pushes ~1,500 shreds in ~18ms at 1 Gb/s and reaches 80% stake in ~2ms, which is why these budgets are feasible.
Don't over-claim a per-round number

Neither whitepaper publishes a single labeled "latency budget per voting round" figure. The defensible facts are: Constellation's 50ms cycle, Alpenglow's ~400ms slot (PoH removed, local clocks instead) trending toward a planned 200ms, and finality at roughly 2x the raw-network lower bound. Treat any exact per-round millisecond budget beyond these as undocumented.

Why erasure coding, not replication, for censorship resistance

This is the "explain why Constellation uses erasure coding rather than replication" skill outcome. The argument has two legs:

  1. An adversary cannot choose which shreds matter. Because any 64 of 256 pshreds reconstruct the pslice, to suppress a proposer's data a censor must stop the data from reaching enough honest attesters - it must control roughly 75% (more than 192 of 256). With replication, a censor only needs to suppress the specific nodes holding the copies, which is a much smaller and more targetable set.
  2. Inclusion is protocol-enforced. A pslice attested by ≥40% of attesters must be included, and the per-pshred hash commitment stops the leader from quietly reordering or dropping it. Censorship stops being a cheap, silent, single-actor choice and becomes an expensive, broad, detectable coalition act.
The 64-of-256 recovery threshold flips the economics of censorship: blocking 64 honest deliveries is cheap, blocking 193 is not.
Honesty flag: Constellation is contested and unratified

Constellation is a live proposal, not finalized protocol. A public critique ("Constellation Is Not Ready For the SIMD", Anagram) argues that a validator can hold both proposer and leader roles in the same cycle (a sandwich-overlap), that ~16 proposer slots are exposed to concentrated validator-as-a-service operators, and that a 40%-attester coalition could selectively withhold attestations without any single overtly malicious act. It also estimates Constellation adds ~75ms of shred-observation latency versus today.

Separately, Rotor's exact Reed-Solomon parameters are deferred to a future SIMD - SIMD-0326 (Alpenglow) explicitly keeps Turbine initially and introduces Rotor later. So treat Rotor's k/n and Constellation's specifics as proposal-stage, not ratified.

Weekly labBuild a Constellation-parameterised encoder

The task, restated

Implement a Constellation-parameterised Reed-Solomon encoder. Run it against the Constellation recovery threshold (any 64 of 256 reconstruct). Then compare byte-for-byte output against the reed-solomon-novelpoly crate to validate correctness.

Erasure coding fundamentals

  • Erasures vs errors. An erasure is a loss at a known position (a shred is simply missing). An error is corruption at an unknown position. A code that corrects t errors corrects 2t erasures, because locating an error costs half the redundancy. Constellation and Rotor deal almost entirely with erasures - a node either has a shred or it does not; integrity is handled separately by hashes and signatures.
  • (n, k) notation. k data shards, n total shards, n - k parity. You recover the original k from any k of the n. For Constellation, k = 64 recovery threshold, n = 256 pshreds.
  • MDS property. Reed-Solomon is Maximum Distance Separable: it meets the Singleton bound (d_min = n - k + 1), meaning any k columns of the generator matrix are independent. That is the algebraic reason "any k of n" works, and it is what makes censorship hard - the adversary cannot pick which shreds count.
  • Recovery threshold = k. The minimum surviving shards to fully reconstruct. Tolerates up to n - k erasures regardless of which ones are lost.

FEC overhead vs replication - quantify it

RS decouples fault tolerance from the storage multiplier; replication does not. As k grows, RS overhead for the same f shrinks toward zero while replication stays linear in f. For the 50ms tick budget, the cost to fit is roughly t_encode + t_transmit + t_decode, where transmit scales by the n / k factor. For Constellation's 64-of-256, the redundancy ratio is 256 / 64 = 4x - generous redundancy bought specifically for censorship resistance, which is the whole point.

Galois field GF(2^8) arithmetic - the engine room

Reed-Solomon does linear algebra over a finite field so the math stays exact and closed (no overflow, every nonzero element has an inverse). For byte-oriented data the natural field is GF(2^8): one byte = one of 256 field elements.

Addition = XOR

Elements are polynomials over GF(2) (bits as coefficients); adding mod 2 is just XOR. Subtraction is identical (since -1 = 1). Example: 0x53 ^ 0xCA = 0x99.

Multiplication = polynomial multiply, then reduce

Multiply the two degree-≤7 polynomials (carryless), then reduce modulo a fixed degree-8 irreducible polynomial so the result fits back in a byte.

One GF(2^8) multiply. The reduction step (XOR a shifted copy of the low byte of the irreducible polynomial whenever a degree-8-or-higher term appears) is what keeps the product inside one byte.

Which irreducible polynomial? It must match the reference

Field-mismatch is the classic silent bug

0x53 * 0xCA = 0x8F under 0x11D, but = 0x01 under 0x11B (they are multiplicative inverses in the AES field). Both are "GF(2^8)" but they are different fields. If your byte-for-byte comparison against reed-solomon-novelpoly fails, the first thing to check is that the irreducible polynomial and generator match exactly. A result of 0x01 for 0x53 * 0xCA means you accidentally built the AES field.

Russian-peasant multiply, and the fast log/antilog table

// GF(2^8) multiply, irreducible 0x11D (low byte 0x1D). Verified results below.
fn gf_mul(mut a: u8, mut b: u8) -> u8 {
    let mut r: u8 = 0;
    for _ in 0..8 {
        if b & 1 == 1 { r ^= a; }      // add current shifted a
        let hi = a & 0x80;             // top bit set? reduction needed after shift
        a <<= 1;
        if hi != 0 { a ^= 0x1D; }      // reduce by low byte of 0x11D
        b >>= 1;
    }
    r
}

Reed-Solomon encode and decode

Systematic encoding means the first k output shards are the original data unchanged; the remaining n - k are parity, computed as GF(2^8) linear combinations of the data.

Systematic RS. The top identity block makes data pass through unchanged; the parity rows (Vandermonde or Cauchy, both MDS) are the redundancy. Decode picks the rows for the shards you still hold, inverts that k x k submatrix, and multiplies.
  • Encoding matrix. An n x k matrix whose top k x k is the identity (systematic) and whose bottom rows make every k x k submatrix invertible. Built from a Vandermonde matrix (row i = powers of a distinct field element) or a Cauchy matrix (1 / (x_i + y_j)), both of which guarantee the MDS condition. Many practical libraries prefer Cauchy for numerical robustness.
  • Decode. Receive any k shards, take the matching k rows of the matrix to form M', invert it over GF(2^8), and compute data = M'^-1 * received. Regenerate any missing parity afterward if needed.

reed-solomon-novelpoly - the validation reference

The lab compares your output against reed-solomon-novelpoly (ParityTech, used in Polkadot's data-availability layer). It is an FFT-based Reed-Solomon using the Lin-Chung-Han "novel polynomial basis" algorithm.

Two gotchas for byte-for-byte parity

Field size differs. novelpoly works over GF(2^16), not the GF(2^8) of the teaching examples above. A naive GF(2^8) encoder will not match it byte-for-byte unless you align the field, shard layout, and basis. The "compare byte-for-byte" exercise is really a test of whether your encoder is parameterized identically to the reference, not just "also Reed-Solomon."

Check n constraints. FFT-based schemes often want n as a power of two. Read the crate's encode/reconstruct signatures and tests in the source before assuming arbitrary n works - this detail was not confirmable from docs alone.

Lab game plan

  1. Implement gf_mul (and log/antilog tables) for your target field; unit-test against the five boundary values above.
  2. Build the systematic encoding matrix (identity block + Vandermonde or Cauchy rows). Verify a small case by hand: every k x k submatrix determinant nonzero.
  3. Encode a pslice into n = 256 shards parameterized to Constellation's k = 64 recovery threshold.
  4. Drop random shards down to exactly 64 survivors; decode; assert you recover the original bytes. Repeat across many random erasure patterns.
  5. Configure your encoder to match reed-solomon-novelpoly's field and layout, run both on identical input, and diff the output byte-for-byte. Investigate any mismatch starting with the field parameters.
  6. Quantify: time encode + decode and check the encode-and-disseminate path could fit a 50ms budget at realistic shard sizes. Note the n/k = 4x bandwidth overhead.

Verify

Why it works: turns the LLM into an adversary generating edge cases (zero, identity, single-reduction, 0xFF*0xFF, field-mismatch canary). You still have to run them - which is where the learning compounds. Answers in the GF(2^8) section.

Debug

Paste a QUIC connection-failure log; ask for an ordered checklist of what to verify in Wireshark.

Why it works: the model proposes a diagnostic procedure rather than a guessed root cause, and you execute it against real captures. Keeps the LLM as a pair-debugger, not an oracle.

A starter Wireshark checklist for a failing QUIC handshake

  1. Filter quic. Confirm an Initial packet leaves the client and an Initial returns from the server (if not: firewall, wrong port, or UDP blocked).
  2. Check Version Negotiation - a VN packet means the client's QUIC version is unsupported.
  3. Inspect ALPN in the TLS ClientHello: for Solana TPU it must be solana-tpu. A mismatch is rejected at handshake.
  4. Look for a Retry packet - the server is doing address validation; confirm the client re-sends an Initial echoing the token.
  5. Watch for early CONNECTION_CLOSE: code maps to the reason. Agave codes include 2 "disallowed" (rate-limited) and 5 "invalid_stream" (oversized stream).
  6. Check transport parameters for stream/data limits, and whether the client got 0 initial uni-streams (it must wait for the stake-based allowance after handshake).
  7. If the connection opens then stalls, look for idle timeout (30s server side) and missing keep-alives.
