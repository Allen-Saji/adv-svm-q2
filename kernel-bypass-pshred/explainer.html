02

The one-sentence thesis

A validator that wants to keep up with the cluster has to receive, sort, and account for hundreds of thousands of small UDP packets per second without the kernel's per-packet tax eating its CPU. Kernel bypass is how.

On a normal Linux socket, every received packet costs you a system call, a context switch, an sk_buff allocation, a full trip through the TCP/IP and netfilter machinery, and at least one memory copy from kernel space into your buffer. At a few hundred thousand packets per second that overhead is your bottleneck, not the work you actually want to do (verifying signatures, reconstructing blocks, voting).

Kernel bypass deletes that tax. You run a tiny program in the driver to decide a packet's fate before the kernel builds any state for it, and for the packets you want, you hand them to userspace through a region of memory the NIC writes into directly. No syscall per packet. No copy. The CPU you save goes back into the validator.

The course framing question ties the whole 6-week program to this:

The framing question

"What does it take to engineer a system that processes erasure-coded pshreds from multiple concurrent proposers inside a 50ms window, achieves Alpenglow consensus in 150ms, and does all of this with enough determinism that a validator never misses a slot?"

Week 2 owns the first clause: getting those pshreds off the wire and sorted, fast.

03

What you need to know walking in

These are the foundations the live sessions assume. None of them are optional, and most trace back to material you have already touched. Each card says what it is, why W2 needs it, and where to go deeper.

The Linux UDP receive path core

What happens to a packet between the NIC and your code: DMA into a ring buffer, hardware interrupt, NAPI poll, sk_buff build, protocol-stack traversal, socket-queue enqueue, and finally a recv() copy into userspace. W2 is entirely about removing steps from this path, so you must know the path it is removing. This is W1 parts 2-3 (the 15-step journey and the six cost centers); re-skim them if "NAPI" or "softirq" feel fuzzy.

Why Solana chose UDP solana

Solana propagates shreds over raw UDP because for block data, speed beats reliability: erasure coding tolerates loss, so a connectionless fire-and-forget transport with no handshake and no head-of-line blocking wins. That same property (unauthenticated UDP) is what makes ingestion a DoS target, which is why transactions later moved to QUIC. Knowing this split (UDP for shreds, QUIC for transactions) is required to place every W2 topic correctly. This is W1 part 1.

Solana ingestion vocabulary: TPU, TVU, shreds, Turbine solana

The TPU (Transaction Processing Unit) is the leader's transaction-ingestion pipeline. The TVU (Transaction Validation Unit) is the non-leader's shred-ingestion pipeline. Shreds are the ~1228-byte fragments a block is split into. Turbine is the tree that propagates them. You will be tracing the TPU receive path "from NIC to replay," so these names must be reflexive. Section 5 below refreshes them.

Rust without the standard library rust

The kernel half of an eBPF program runs in a sandbox with 512 bytes of stack, no heap, and no std. You write it in no_std Rust: core instead of std, no allocations, no panic!, every packet access wrapped in unsafe with a manual bounds check. If you have only written std Rust, spend an hour with #![no_std] and raw-pointer access before Tuesday.

Lock-free SPSC ring buffers rust

Both AF_XDP and io_uring are built on single-producer / single-consumer ring buffers in shared memory: one side writes at a producer index, the other reads at a consumer index, and a memory fence (not a lock, not a syscall) synchronizes them. Understanding why an SPSC ring needs no lock, and what a producer/consumer index pair is, is the conceptual key to the whole week. (It also connects to the W1 lab's loom-tested lock-free work.)

The NIC / DMA / queue model core

A modern NIC has multiple hardware receive queues and can DMA incoming frames straight into host memory. Features like RSS (receive-side scaling) and flow steering decide which queue a packet lands in. AF_XDP binds one socket to one queue, so "which queue" is a real design variable in your lab. You do not need to be a driver author, but you need the mental model: NIC -> DMA -> per-queue ring -> driver poll.

04

Every acronym on the card

The fast reference. Click any term to expand it. The heavy ones get their own full deep-dive in Section 05. Terms are grouped by the layer they live in, NIC-upward.

Layer 1: programmable code inside the kernel

eBPF verifier · maps · JIT

extended Berkeley Packet Filter. A way to run small, sandboxed programs inside the Linux kernel without writing a kernel module or patching the kernel. You compile restricted C or Rust to eBPF bytecode (a 64-bit RISC-like instruction set), the kernel statically checks it for safety, JIT-compiles it to native machine code, and runs it at a "hook" point. eBPF powers modern Linux observability, security, and networking. For W2 it is the substrate: an XDP program is an eBPF program.

The eBPF verifier why your program gets rejected

The static analyzer that every eBPF program must pass before it loads. It simulates all execution paths and proves the program is safe: no uninitialized reads, no out-of-bounds memory access, no unbounded loops, only whitelisted helper calls, stack under 512 bytes, complexity under ~1 million analyzed instructions. It is strict because your code runs with full kernel privilege; a bug would corrupt kernel memory or hang the machine. "Get it past the verifier" is the single hardest part of writing XDP. Full treatment in Section 05.

BPF maps array · hash · per-CPU · ringbuf

Typed key-value stores in kernel memory that an eBPF program shares with userspace (and with its own future invocations, since the program itself is stateless between packets). Key types you will meet: ARRAY / HASH (general storage), PERCPU_* (one slot per CPU, so counters need no lock), RINGBUF (stream events to userspace), and the star of this week, XSKMAP.

XSKMAP the steering table

BPF_MAP_TYPE_XSKMAP. A map whose entries are AF_XDP socket handles, indexed by an integer. When your XDP program calls bpf_redirect_map(&xskmap, key, 0), the packet is steered into the AF_XDP socket sitting at that key. This is the mechanism your lab uses to send proposer A's pshreds to queue A and proposer B's to queue B. Only userspace can write this map, never the BPF program.

Layer 2: the earliest hook (XDP) and how you write it (aya)

XDP eXpress Data Path

An eBPF program that runs in the NIC driver, in the poll loop, before the kernel allocates an sk_buff. It sees the raw packet first and returns a verdict: XDP_DROP (kill it at line rate), XDP_PASS (let the kernel handle it normally), XDP_TX (bounce it back out), XDP_REDIRECT (send it elsewhere: another NIC, another CPU, or an AF_XDP socket), or XDP_ABORTED (error). Because it runs before any kernel state is built, dropping or redirecting here is extremely cheap. Section 05 has the full anatomy.

Hook points / attach modes native · offload · generic

Where the XDP program physically runs. Native (driver) mode runs it in the NIC driver: fast, the real thing, needs driver support. Offloaded mode runs it on a SmartNIC's own chip: fastest, no host CPU at all, needs special hardware. Generic (SKB) mode runs it as a software shim after the sk_buff already exists: works on any NIC, gives no speed benefit, good only for testing. Tuesday's "hook points" means choosing among these.

aya-rs eBPF in pure Rust

A pure-Rust eBPF framework with no C, no libbpf, no LLVM at runtime. Your project splits into two crates: an eBPF crate compiled to the bpfel-unknown-none target (no_std, this is the kernel-side program, written with the #[xdp] macro) and a userspace crate (normal std Rust that loads the bytecode, attaches it, and reads the maps). "Write a pshred classifier with aya-rs" means: author both crates. Section 05 shows the skeleton.

Layer 3: getting packets to userspace fast

AF_XDP XDP sockets · XSK

A socket address family that lets userspace receive raw frames at high speed: an XDP program REDIRECTs chosen packets into a shared-memory region the socket owns, skipping the rest of the kernel stack. It is built from a shared buffer (UMEM) and four lock-free rings (FILL, RX, TX, COMPLETION). This is the kernel-bypass mechanism of the week. Section 05 dissects the rings.

UMEM the shared packet pool

User Memory. A contiguous region of your memory, sliced into equal 2KB or 4KB frames, registered with the kernel and memory-mapped so the NIC can DMA packets directly into it. This shared region is the "shared-memory model" the skill outcome asks you to explain: because the buffer is visible to both kernel and userspace, there is no copy across the boundary in zero-copy mode.

The four rings FILL · RX · TX · COMPLETION

Four single-producer/single-consumer ring buffers that coordinate UMEM frames without syscalls. FILL: you hand the kernel empty frames to fill. RX: the kernel hands you descriptors of received packets. TX: you hand the kernel frames to send. COMPLETION: the kernel hands back frames it finished sending. The "fill ring replenishment loop" in the AI section is the discipline of keeping FILL stocked. Section 05 diagrams all four.

Fill ring starvation the failure mode

If you stop refilling the FILL ring with empty frames, the NIC has nowhere to DMA incoming packets and drops them at the hardware. Worse, because FILL is shared between the bypass path and the normal kernel path, an empty FILL ring can drop even XDP_PASS traffic (your SSH session included). The Wednesday AI exercise is to construct exactly this scenario from a replenishment loop. Section 06.

Zero-copy vs copy mode driver-dependent

Zero-copy: the NIC DMAs the packet directly into your UMEM frame, no CPU copy. Needs driver support (i40e, ice, ixgbe, mlx5, and friends). Copy mode: the kernel copies the packet into UMEM for you. Still far faster than the full stack (no sk_buff, no protocol traversal), just not zero-copy. You request a mode at bind time and fall back if the driver cannot.

io_uring the async cousin

A Linux async I/O interface built on the same idea as AF_XDP: two shared-memory rings (a Submission Queue and a Completion Queue) so you batch many operations with few or zero syscalls. In SQPOLL mode a kernel thread polls your submission ring, so you submit work with zero syscalls, just a memory write. It generalizes beyond storage to network I/O and even zero-copy receive. W2 relates it to AF_XDP to show that "shared-memory rings to kill syscalls" is a general pattern, not an XDP quirk.

DPDK total bypass

Data Plane Development Kit. The maximalist option: unbind the NIC from the kernel entirely, drive it from userspace with a poll-mode driver on hugepages, and reimplement networking yourself. Highest throughput, but the NIC vanishes from the kernel (tcpdump and ethtool can no longer see it), it pins whole cores at 100% CPU, and you own the whole stack. The contrast to AF_XDP (which keeps the NIC in the kernel and bypasses selectively) is a Tuesday talking point. Section 05 compares them.

Layer 4: the Solana ingestion target

TPU fetch · sigverify · banking · broadcast

Transaction Processing Unit: the leader-side pipeline that turns incoming transactions into a block. Stages, in order: Fetch (receive packets, now over QUIC), SigVerify (dedup + signature checks), Banking (schedule and execute, the core), Broadcast (split entries into shreds and propagate). "Trace the Agave tpu.rs receive path from NIC to replay" means following this. Section 05.

QUIC-only TPU ingestion UDP -> QUIC

Solana originally took transactions over raw UDP, which was a trivial DoS target (no identity, no rate limit, no backpressure). It moved transaction ingestion to QUIC (the UDP-based transport behind HTTP/3) to get connection identity, per-sender rate limiting, and stake-weighted QoS (higher-staked peers get more throughput). The catch: handling thousands of QUIC handshakes at high rate is itself expensive, which is the motivation for kernel-bypass QUIC ingestion. Implemented with the quinn crate in streamer/src/quic.rs.

Shreds data · coding · Reed-Solomon

The ~1228-byte fragments a block is split into for propagation. Data shreds carry transaction entries; coding shreds are Reed-Solomon parity that lets a receiver reconstruct missing data shreds (a typical set is 32 data + 32 coding, any 32 of 64 rebuild the block). Sent over UDP via Turbine, Solana's tree-based propagation protocol. Shreds are the model that pshreds are named after.

pshred Constellation / MCP

"proposal shred." From Anza's Constellation proposal (Multiple Concurrent Proposers), not from DoubleZero. A proposer assembles transactions into a pslice every 50ms, erasure-codes it into 256 pshreds, and sends one to each of 256 attesters (any 64 reconstruct the pslice). The "p" distinguishes them from Turbine shreds. Important: there is no public byte-level pshred wire format yet, so the "source-identifier field in the UDP payload" your lab demuxes on is a course-defined target spec, not a documented protocol field. Section 05 is explicit about this.

Per-proposer queues demultiplex by source

In a multi-proposer world, up to ~16 proposers send pshreds to the same validator on the same port at once. If they all land in one socket buffer, one noisy proposer can crowd out the others, which defeats the censorship-resistance goal. Demultiplexing means reading a source identifier from each packet and routing it to a per-proposer queue (one AF_XDP socket per proposer) for isolation, QoS, and parallel draining. This is the lab.

DoubleZero thursday guest

A decentralized physical network ("DePIN for bandwidth") of private fiber links dedicated to high-performance blockchains, founded by Austin Federa (ex-Solana Foundation) and the Malbec Labs team. It filters spam and verifies signatures at the network edge on FPGAs, then carries clean traffic over dedicated low-jitter fiber, with multicast for shred distribution. It is integrated into Agave, Firedancer, and Jito. Section 07 explains why their engineers are the perfect W2 guests.

The heavy ones, expanded

The five topics that carry the week and reward real understanding: the verifier, the XDP program itself, the AF_XDP rings, the bypass spectrum, and the Agave TPU path.

5.1  The eBPF verifier: why your program keeps getting rejected

An eBPF program runs with kernel privilege. There is no process boundary protecting the machine from it. So before the kernel will load your bytecode, the verifier walks every possible path through it and proves it cannot do harm. This is the gate the AI "Debug" exercise is about: you paste a rejection, and you learn which invariant you violated.

What the verifier enforces, in the terms you will see in error messages:

  • Bounded termination. No unbounded loops. Before kernel 5.3 every backward jump was rejected outright; since 5.3 the verifier accepts loops it can prove terminate, and bpf_loop() gives an explicit bounded-iteration helper.
  • Memory safety with manual bounds checks. You cannot dereference a packet pointer until you have proven, in code, that it is in range. The canonical pattern is if (data + sizeof(hdr) > data_end) return XDP_DROP; before reading hdr. Forget it and the verifier rejects with an out-of-bounds access error.
  • No uninitialized reads of registers or stack.
  • 512-byte stack ceiling. No heap at all. This is why the kernel crate is no_std and allocation-free.
  • Whitelisted helpers only. A program can only call the helper functions permitted for its program type. An XDP program cannot call helpers reserved for, say, tracing.
  • Null checks after map lookups. bpf_map_lookup_elem() returns a maybe-null pointer; use it without a null check and you are rejected.
  • Complexity budget. The verifier caps total analyzed instructions around 1,000,000 (privileged) or 4,096 (unprivileged). A program too branchy to analyze within budget is rejected even if it is correct.
The mental shift

You are not writing code the compiler accepts. You are writing code a theorem prover accepts. A correct program can still be rejected for being too complex to prove correct. The skill is writing code that is obviously safe to the verifier: bounds-check immediately, keep branches shallow, prefer per-CPU maps, and read verifier output as a proof obligation you failed to discharge.

5.2  The XDP program: context, bounds, verdict

An XDP program receives one argument, a context (xdp_md) carrying two pointers, data (start of the packet) and data_end (one past the end), plus the receive queue index. Your job: parse just enough of the headers to make a decision, bounds-checking every step, then return a verdict.

VerdictValueMeaning
XDP_ABORTED0Program hit an error; drop + fire a tracepoint. Treat as a bug.
XDP_DROP1Drop here, in the driver, before any kernel state. Line-rate DDoS filtering lives here.
XDP_PASS2Hand to the normal kernel stack (possibly after you modified it).
XDP_TX3Send it back out the same NIC (hairpin load balancers).
XDP_REDIRECT4Send elsewhere via a map: another NIC (DEVMAP), another CPU (CPUMAP), or an AF_XDP socket (XSKMAP). Your lab returns this.

Verdict integer values are consistent across sources but worth confirming against include/uapi/linux/bpf.h in your kernel tree.

For the pshred forwarder, the body is: parse Ethernet -> IP -> UDP (bounds-checking at each layer), read the source-identifier field at the agreed offset in the UDP payload, map it to a queue index, and bpf_redirect_map(&xsks, queue_idx, 0). That single redirect is what moves the packet into the right per-proposer AF_XDP socket.

Why two crates

The kernel crate targets bpfel-unknown-none and is linked by bpf-linker into eBPF ELF bytecode, not a native binary. The userspace crate embeds that bytecode and is an ordinary async Rust program that can use tokio, read counters out of maps, and manage the sockets. The split mirrors the privilege boundary: untrusted-but-verified code in the kernel, full-power control plane in userspace.

5.4  The four AF_XDP rings (and how to starve them)

Once the XDP program redirects a packet into an AF_XDP socket, userspace picks it up through shared-memory rings. There are four, each single-producer/single-consumer, each just a producer index and a consumer index over a slice of shared memory. Two are for receive, two are for transmit.

FILL ring
You hand the kernel addresses of empty UMEM frames: "here are buffers to put incoming packets in."
userspace -> kernel
RX ring
The kernel hands you descriptors of received packets: which frame, what length. You read the packet straight out of UMEM.
kernel -> userspace
TX ring
You hand the kernel frames to transmit.
userspace -> kernel
COMPLETION ring
The kernel hands back frames it has finished sending, so you can reuse them.
kernel -> userspace

The receive cycle is a loop: drain RX, process each packet, and immediately recycle each consumed frame back onto FILL so the NIC always has somewhere to write. The flush of the producer index (a memory fence, not a syscall) is what makes the new entries visible to the other side.

Fill ring starvation: the Wednesday exercise

If your loop stops returning frames to FILL fast enough (held too long for processing, or an off-by-one on the producer index, or a flush that races the descriptor write), FILL empties. The NIC then has no buffer to DMA into and drops packets at the hardware. The subtle, dangerous part: FILL is shared with the kernel's own receive path, so starvation can drop even XDP_PASS traffic, meaning your management SSH dies along with your pshreds. "Ask AI to construct a scenario that starves the ring" is asking you to reason precisely about producer/consumer index timing.

Why this kills syscalls

In a normal socket, every packet is a recv(): one syscall, one context switch, a copy. With AF_XDP, the rings live in memory shared with the kernel. To get a packet you read the RX ring's producer index from memory; to give back a frame you write the FILL ring. No syscall on the hot path. The only syscalls are the optional poll() / sendto() "wakeup" kicks, and the XDP_USE_NEED_WAKEUP flag lets you skip even those unless the kernel asks. That is exactly the "shared-memory model that avoids syscalls on the hot path" the skill outcome wants you to explain.

For a Solana validator handling sub-1500-byte UDP shreds, AF_XDP is the pragmatic choice (it is what Firedancer uses and what Agave added in 2.3.8): you keep the kernel's UDP stack for control traffic and Rust's safe concurrency, and bypass only the hot path. DPDK would only win if AF_XDP's per-packet floor ever proved insufficient at validator packet sizes, which it has not. io_uring sits to the left as the proof that the ring pattern is general: SQPOLL eliminates submit syscalls the same way AF_XDP eliminates receive syscalls, while keeping the full kernel stack.

5.6  The Agave TPU receive path: NIC to replay

The "Navigate" exercise asks you to trace every channel from the NIC to replay in tpu.rs. Here is the map. Leader path (transactions in over QUIC) on the left logic, validator path (shreds in over UDP) on the right.

            NIC
             |
   QUIC (transactions)          UDP (shreds, port 8002)
             |                            |
   [QUIC streamer]  quinn          [ShredFetch]  SO_REUSEPORT

             |  PacketBatch               |

The thing to internalize: the stages are wired by crossbeam channels (mostly unbounded mpsc), and the whole pipeline is what W2's kernel-bypass work feeds. Today, packets arrive through the kernel and get copied into PacketBatches at the fetch boundary. The W2 thesis is to replace that boundary with an AF_XDP path so packets land in userspace with no syscall and no copy, which is precisely how Firedancer's net tile already works. Tracing the channels by hand is how you find where the fast path would splice in.

The lab: an XDP pshred forwarder

Build an XDP program that reads a source-identifier field from each pshred's UDP payload and routes it to a per-proposer AF_XDP queue. That is the entire deliverable, and every concept above is a piece of it.

Honesty about the "target specification"

The card says to use "the pshred format described in the Constellation whitepaper as the target specification." Two corrections from primary sources: (1) Constellation is Anza's proposal, not a DoubleZero document. There is no "DoubleZero Constellation whitepaper." (2) Constellation describes pshreds conceptually (a pslice erasure-coded into 256 pieces, 64-of-256 recovery, with a cryptographic commitment) but publishes no byte-level wire format. So the "source-identifier field at offset N in the UDP payload" is a course-defined target spec for the exercise, architecturally coherent with how multi-proposer routing would work, not a field you will find documented in any spec today. Build to the spec the cohort gives you; do not invent protocol bytes and present them as canonical.

Numbers to calibrate against

  • 10GbE line rate, 64-byte frames: ~14.88 million packets/sec. That is the physical ceiling you are chasing.
  • Plain socket baseline: roughly 1-2 Mpps before the CPU saturates on syscall + copy overhead.
  • AF_XDP zero-copy: ~16.9 Mpps rxdrop in the canonical 2018 Linux Plumbers benchmark (40GbE, i40e); real single-core 10GbE setups land around 10-11 Mpps.
  • XDP_DROP alone: ~26 Mpps/core, the upper bound on how fast the XDP layer itself can run before any userspace handling.

Treat editorial latency tables (socket vs io_uring vs AF_XDP vs DPDK in microseconds) as directional. The ordering is reliable; the exact figures depend heavily on NIC, kernel, and NUMA layout. Always cite your own measured baseline.

The three AI exercises, decoded

Debug // the verifier

Paste the full eBPF verifier rejection. Ask for the specific constraint violated and three ranked fixes to test. Why this works: verifier output is dense and points at an instruction, not a cause. Forcing a ranked hypothesis list turns a wall of register-state text into a debugging plan. This is the single highest-leverage AI use of the week.

Verify // ring starvation

Paste your fill-ring replenishment loop. Ask AI to construct a scenario that starves the ring. Why this works: starvation is a timing bug between producer and consumer indices; it will not show up in a happy-path test. Asking for an adversarial schedule surfaces the off-by-one or the missed flush before production traffic does.

Navigate // tpu.rs

Paste the Agave tpu.rs receive path. Ask AI to trace every channel from NIC to replay. Why this works: the pipeline is wired by many crossbeam channels across files. A traced channel map tells you exactly where an AF_XDP fast path would splice in, which is the point of learning the path at all.

Program-wide trust rule (carry it into this lab)

Per the cohort's AI trust calibration: never trust an AI claim about XDP verifier constraint satisfaction, kernel API versions, struct offsets, or unsafe correctness without verifying by hand. Use AI to generate hypotheses and traces; verify the kernel-boundary specifics against the actual headers, docs, and a running verifier.

Why this is worth a whole week

Because Solana's bottleneck has moved from compute to communication, and this is the layer where that fight is being won.

The performance of a modern processor is rarely limited by its cores; it is limited by moving data between them. The same is now true of Solana: validators are increasingly bottlenecked by bandwidth and latency between nodes, not by execution inside them. That is why a stack of independent efforts is converging on the network layer, and they compound:

Why DoubleZero is the perfect Thursday guest: their production network is this stack, made physical. They filter spam and verify signatures at the edge on FPGAs (hardware packet processing, the sibling of what XDP does in software), carry clean traffic over dedicated fiber, and use multicast for shred fanout. Anza even extended Agave's XDP to work over GRE tunnels specifically so validators can combine XDP's speed with DoubleZero's low-jitter backbone (the "IBRL" mode: Increase Bandwidth, Reduce Latency). The end-to-end path they can speak to is exactly the one you are building a slice of: internet edge -> FPGA filter -> GRE tunnel -> XDP ingress at the validator NIC -> AF_XDP zero-copy into the validator process.

And why it matters for an infra-tier career: app-tier Solana work stops at the program boundary. This is the work below the API line, where the validator earns or loses its slot. Being able to write a verified XDP classifier, reason about ring starvation, and trace the Agave ingestion path cold is the difference between using the validator and being able to make it faster.
