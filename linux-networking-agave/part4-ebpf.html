Part 4

Safe Programmable Code
Inside the Kernel

The kernel is fast but rigid. Kernel modules are flexible but dangerous. eBPF splits the difference: run your own code in kernel space, verified safe before a single instruction executes.

01

The Problem eBPF Solves

Part 3 showed why the kernel's default networking stack breaks under validator load. The fix sounds obvious: run custom logic inside the kernel. Drop spam packets before they cost anything. Steer traffic to the right place. Observe without overhead.

But the traditional way to extend the kernel is kernel modules. They run in ring 0. A bug in a kernel module doesn't just crash your program; it crashes the entire machine. They're version-coupled (recompile for every kernel update), require root to load, and are notoriously hard to audit.

So the question is: can you run custom code inside the kernel safely, without risking a crash, without being locked to a kernel version, and without becoming a security liability?

The answer is eBPF. And if you've written Solana programs, the architecture should feel eerily familiar.

02

Classic BPF (1993): Where It Started

1993
Berkeley Packet Filter
The problem was tcpdump. Without BPF, when you ran tcpdump on a busy interface, the kernel copied every single packet to userspace. Your filter ran there, discarding 99% of what it received. On a link pushing thousands of packets per second, this was untenable.
McCanne and Jacobson's insight: put a tiny virtual machine inside the kernel. Compile the filter expression to bytecode. Run it in the kernel. Only copy matching packets up to userspace.
Steven McCanne & Van Jacobson, Lawrence Berkeley Lab
1993 - 2013
Intentionally Limited
Classic BPF was deliberately constrained. 2 registers (A and X). 32-bit operations only. Forward-only jumps, so no loops and guaranteed termination. A hard limit of ~4,096 instructions. Programs could only attach to sockets. These limits made it safe but narrow. It was a packet filter, nothing more.
2014
Extended BPF (eBPF)
Alexei Starovoitov at Facebook generalized BPF into a full in-kernel VM. More registers, 64-bit operations, maps for shared state, helper functions, and the ability to attach programs to dozens of kernel hook points, not just sockets. The shift: from "filter packets" to "run safe programs at any kernel hook point."
Alexei Starovoitov, Facebook/Meta
2018+
Ecosystem Explosion
BTF (BPF Type Format) for portable programs. CO-RE (Compile Once, Run Everywhere). libbpf, bpftool, Cilium, Falco, Katran. eBPF went from a kernel subsystem to a platform powering production networking, security, and observability at hyperscaler scale.

When you type tcpdump "udp port 8004", that filter expression compiles to BPF bytecode. The kernel runs it against every incoming packet on the socket. Only packets matching port 8004 get copied to userspace.

03

Extended BPF (2014+): The Generalization

The 2014 rewrite didn't just add features to BPF. It turned a packet filter into a general-purpose in-kernel execution environment. Every constraint from classic BPF was loosened or removed, while the core safety guarantee remained: programs are verified before execution.

Feature Classic BPF (1993) eBPF (2014+)
Registers 2 (A and X) 11 (R0 - R10)
Width 32-bit 64-bit
Instruction limit ~4,096 1,000,000+
Maps (shared state) No Yes (hash, array, ringbuf, LRU, ...)
Helper functions No Yes (hundreds of whitelisted helpers)
Attach points Sockets only XDP, tc, kprobe, tracepoint, cgroup, LSM, ...
JIT compilation Optional Default (native speed)

The key shift in thinking: BPF went from "filter packets on sockets" to "extend the kernel without writing a kernel module." Any hook point the kernel exposes can have an eBPF program attached. Networking, tracing, security, scheduling. The program runs at native speed after JIT compilation, with the kernel's guarantee that it can't crash the system.

04

The Verifier: The Gatekeeper

This is the most important piece of eBPF. When you load a program into the kernel, the verifier runs before the program ever executes a single instruction. If the verifier rejects it, the program never loads. If the verifier accepts it, the program is JIT-compiled to native machine code and runs with zero runtime safety checks.

All the safety is front-loaded. The verifier is the single gate between untrusted bytecode and kernel execution.

05

Maps and Helpers

eBPF programs run inside the kernel, but they need two things: persistent state (to remember things between invocations) and kernel capabilities (to actually do useful work). Maps provide the first. Helpers provide the second.

Maps: Shared State Between Worlds

Maps are key-value data structures that live in kernel memory but are accessible from both eBPF programs (kernel side) and userspace applications. They're the bridge.

The eBPF Maps Bridge
eBPF Program
Runs in kernel. Reads/writes maps at wire speed.
BPF Map
Kernel memory. Key-value store. Shared access.
Userspace App
Config, monitoring, dashboard. Reads/updates maps via bpf() syscall.
HASH
General key-value. IP allowlists, per-source rate counters.
ARRAY
Fixed-size, O(1) index lookup. Config tables, statistics.
LRU_HASH
Bounded size with LRU eviction. Connection tracking without OOM risk.
RINGBUF
Efficient kernel-to-userspace event stream. Tracing, metrics export.
XSKMAP
Maps XDP sockets to NIC queues. The key to AF_XDP zero-copy I/O.
Validator Use Cases

A validator's eBPF programs use maps to store an IP allowlist (hash map, updated from userspace when stake weights change), per-source rate counters (LRU hash, auto-evicting stale entries), and AF_XDP socket routing tables (XSKMAP, directing packets to specific receive queues).

Helpers: Whitelisted Kernel Functions

eBPF programs can't call arbitrary kernel functions. They can only call explicitly exposed helper functions. Each helper is a stable API the kernel promises to maintain. This is how eBPF programs interact with kernel subsystems without coupling to kernel internals.

bpf_map_lookup_elem()
Read a value from a BPF map by key
bpf_xdp_adjust_head()
Modify packet headers (add/remove encapsulation)
bpf_redirect_map()
Redirect packet to another interface or AF_XDP socket
bpf_ktime_get_ns()
Get current kernel timestamp in nanoseconds

The parallel to Solana is direct. On-chain programs can't call arbitrary Rust functions. They can only call syscalls the runtime exposes: sol_invoke_signed, sol_log, sol_create_program_address. Same boundary, same reason: safety and stability.

06

Four Networking Capabilities

With maps for state, helpers for kernel interaction, and the verifier for safety, eBPF gives networking code four superpowers. These are the building blocks that Agave's networking stack relies on.

Observe
Count packets, drops, flows, latency, queue depth. All at wire speed with near-zero overhead. No sampling, no approximation, no userspace copy.
tracepoint, kprobe, perf_event
Filter
Reject traffic before later stages do more work. Drop spam before sk_buff allocation. Discard malformed packets before they touch the socket buffer.
XDP_DROP, tc ingress
Classify and Steer
Parse headers, choose policy, select queue, pick CPU, redirect to a target. Protocol-aware load balancing at driver level, before the kernel networking stack even sees the packet.

Enforce
Apply allowlists, deny rules, rate limits, protocol checks. A programmable firewall faster than iptables: O(1) map lookup vs O(n) rule chain traversal.

What Comes Next

Bridge to Part 5

eBPF gives us the ability to run safe code in the kernel. But where we attach that code determines how much overhead we skip. A program at the tc (traffic control) layer still pays for sk_buff allocation. A program at a kprobe still pays for the full network stack traversal.

The next part introduces XDP: the earliest possible eBPF hook point, right at the NIC driver, before the kernel allocates a single data structure. That's where validators get the speed they need.
