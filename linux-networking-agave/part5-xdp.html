Part Five

XDP: The Early Hook That Drops Packets Before They Cost Anything

Part 4 introduced eBPF as safe, programmable code inside the kernel. Now we hook that code at the earliest possible point in the networking stack: inside the NIC driver itself, before the kernel allocates a single data structure.

01

Where XDP Sits

Recall the 15-step path from Part 2. XDP (eXpress Data Path) is an eBPF program that runs inside the network driver, right after step 5: the driver has harvested the raw packet buffer from the DMA ring, but before sk_buff allocation. This is the earliest possible software hook point in the Linux kernel.

The 15-Step Path: Where XDP Hooks In
01 NIC receives frame from the wire
02 DMA writes frame into pre-mapped ring buffer
03 NIC raises hardware IRQ
04 IRQ handler schedules NAPI poll (softirq)
05 Driver RX poll harvests raw packet buffer
XDP RUNS HERE
eBPF program executes on raw DMA buffer. No sk_buff yet. Decides: DROP / PASS / TX / REDIRECT
Skipped on XDP_DROP or XDP_REDIRECT
06 sk_buff allocation (~240 bytes metadata)
07 GRO aggregation
08 netif_receive_skb / RPS distribution
09 tc (traffic control) ingress qdisc
10 Netfilter PREROUTING chain
11 IP routing decision
12 Netfilter INPUT / FORWARD chain
13 UDP protocol handler
14 Socket lookup + receive queue
15 recvmsg() copies to userspace

Key Insight

12x metadata reduction. Still running in kernel space (ring 0, within the NAPI poll function), but the packet has not entered the full network stack yet. That distinction is everything.

02

The Four Verdicts

Every XDP program returns exactly one of four integer constants. Each one tells the driver what to do with the packet right now. No queuing, no deferral. The verdict executes inside the NAPI poll loop.

XDP_DROP
Discard immediately. The driver recycles the RX ring buffer slot. Cost: one pointer write. No sk_buff, no stack traversal, no notification. The packet ceases to exist. This is the big win for spam filtering.
~50-100ns total per packet
packet /dev/null
XDP_PASS
Let the packet continue into the normal kernel stack. From here, identical to a world without XDP. sk_buff gets allocated, full 15-step path proceeds. The default for legitimate traffic.
Normal stack cost (~800-1500ns)
packet kernel stack
XDP_TX
Transmit back out the same NIC. Can modify packet contents first (swap src/dst MAC addresses). Useful for hairpin load balancers, ICMP echo at line rate. Less relevant for validators.
~100-200ns (rewrite + TX ring)
packet same NIC TX
XDP_REDIRECT
Send to a different target via bpf_redirect_map(): another NIC, an AF_XDP socket (via XSKMAP), or another CPU (via CPUMAP). This is the key action for kernel bypass.
~150-300ns (map lookup + redirect)
packet AF_XDP / NIC / CPU
03

What XDP Skips (on DROP/REDIRECT)

When the verdict is XDP_DROP or XDP_REDIRECT, the packet never touches the kernel network stack. Here is exactly what gets bypassed:

Bypassed on XDP_DROP / XDP_REDIRECT
No sk_buff allocation -- no 240-byte struct, no slab cache hit
No IP/UDP parsing -- only the eBPF program parses what it needs (lazy parsing)
No netfilter -- no iptables chain traversal, no conntrack
No socket lookup -- these only happen if XDP_PASS is returned
No context switch -- same core, cache-hot, inside the NAPI poll, no scheduling
7-14 sec of CPU/sec saved
At 9M spam pps dropped by XDP, saving ~800-1500ns per packet
Why This Matters

Without XDP, 9 million spam packets per second would each consume 800-1500ns of kernel stack traversal. That is 7 to 14 seconds of CPU time every second. A single core only has 1 second of time per second. XDP turns that into 0.45-0.9 seconds across all cores, dropping each packet in 50-100ns.

04

Raw Frame Parsing

XDP programs read raw Ethernet frames starting at Layer 2. Every pointer dereference needs a bounds check against data_end, or the eBPF verifier rejects the program at load time. No exceptions.

C / eBPF
// Parse Ethernet header
struct ethhdr *eth = (void *)(long)ctx->data;
if ((void *)(eth + 1) > (void *)(long)ctx->data_end)
    return XDP_DROP;     // packet too short for eth header

if (eth->h_proto != htons(ETH_P_IP))
    return XDP_PASS;     // not IPv4, let kernel handle

// Parse IP header
struct iphdr *ip = (void *)(eth + 1);
if ((void *)(ip + 1) > (void *)(long)ctx->data_end)
    return XDP_DROP;     // packet too short for IP header

if (ip->protocol != IPPROTO_UDP)
    return XDP_PASS;     // not UDP, let kernel handle TCP

// Parse UDP header
struct udphdr *udp = (void *)ip + ip->ihl * 4;
if ((void *)(udp + 1) > (void *)(long)ctx->data_end)
    return XDP_DROP;

// Now decide based on port, source IP, rate limit...

This is "lazy parsing." You only touch the bytes your decision requires. For a spam drop based on source IP, you might read 30 bytes out of a 1232-byte packet.

Parse Ethernet + IP + UDP headers. Read 30-42 bytes. Skip everything else. Decision in 50-100ns.

05

Three XDP Modes

Not all XDP is equal. The mode determines where your eBPF program actually executes, which controls both performance and hardware requirements.

Recommended
Native XDP
Runs inside the NIC driver's NAPI poll function. Before sk_buff allocation.
Best
Requires: driver support (mlx5, ice, i40e, ixgbe, virtio-net)
Minimum for validators
Fallback
Generic XDP
Runs after sk_buff allocation, inside netif_receive_skb. Same as a tc-BPF hook.
Slower
Requires: any NIC, any driver. Works everywhere.
Defeats the purpose
Ideal
Offloaded XDP
Runs on the NIC hardware itself. Zero CPU cycles consumed for packet processing.
Fastest
Requires: Netronome Agilio SmartNICs only
Very limited hardware
Validator Guidance

Native XDP is the minimum. Generic XDP still allocates sk_buff before your program runs, which defeats the entire point. Offloaded XDP is the dream but currently limited to Netronome Agilio SmartNICs, which are niche hardware.

06

Decision Flow for a Validator

A typical Agave validator XDP program implements a decision tree. Each branch is cheap: a comparison, a map lookup, or a counter check. The entire program runs in under 100ns.

Validator XDP Decision Tree
Packet arrives at XDP hook
Not IPv4?
XDP_PASS
Not UDP?
XDP_PASS
Source IP not in allowlist map?
XDP_DROP
Rate limit exceeded for source?
XDP_DROP
UDP port = QUIC port?
REDIRECT AF_XDP 0
UDP port = Turbine port?
REDIRECT AF_XDP 1
UDP port = gossip port?
XDP_PASS
Unknown port?

Notice the pattern: non-UDP traffic passes through to the kernel (TCP for RPC, ARP, IPv6). The XDP program only intervenes on UDP, where Solana's transaction and block data flows. Gossip goes through the normal stack because it is lower volume and benefits from kernel TCP/UDP handling.

QUIC and Turbine traffic get XDP_REDIRECT to AF_XDP sockets, which bypasses the kernel entirely for good packets. That is the subject of Part 6.

Real-World: Cloudflare

Cloudflare's L4Drop system uses XDP in native mode for DDoS mitigation at global scale. Their production numbers confirm everything about XDP's cost model.

During one attack, a 40x increase in packet volume only caused CPU usage to rise ~10%. The XDP program's per-packet cost is so low that even massive floods barely register. Cloudflare processes 50-300M pps network-wide on normal days using the same XDP infrastructure.

Validator Parallel

A Solana validator under spam attack faces the same problem at smaller scale. Where Cloudflare drops DDoS floods, validators drop duplicate transactions, malformed QUIC packets, and traffic from unknown peers. Same tool, same economics. XDP_DROP is the cheapest discard primitive Linux offers.
