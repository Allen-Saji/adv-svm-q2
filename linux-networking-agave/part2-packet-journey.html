Part 2

The Packet's Journey

A UDP datagram hits your NIC. Before it reaches a single line of Agave code, it travels through 13 steps across four kernel layers. This is the full Linux UDP receive path: general, compatible, observable, and expensive.

01

The Big Picture

Every UDP packet your validator receives follows this exact path through the Linux kernel. No exceptions. No shortcuts. From the moment the Ethernet frame hits the wire to the moment bytes land in your application buffer, the kernel executes a deterministic sequence of operations.

The path splits into four layers. Each layer has a different job, a different cost profile, and different tuning knobs. Click any step to scroll to its detailed breakdown.

02
L1
Layer 1: NIC & Driver

Hardware to Kernel Handoff

The packet begins its life on the wire. Before any software runs, hardware does the heavy lifting: accepting the frame, writing it to memory, and signaling the CPU. These five steps happen millions of times per second on a busy validator.

1
NIC Receives the Frame

An Ethernet frame arrives on the physical link. The NIC's MAC filter checks the destination MAC address. If it matches the interface (or a multicast/broadcast group the NIC subscribes to), the frame is accepted. Otherwise it's dropped in hardware before any CPU involvement.

For a validator receiving Turbine shreds, gossip messages, and QUIC datagrams, this is the first gate. The NIC's MAC filter is extremely fast but imprecise. It only filters by Layer 2 address, not by IP or port.

2
DMA Into the RX Ring Buffer

The NIC writes the raw Ethernet frame directly into host memory via DMA (Direct Memory Access). Zero CPU involvement. The target is a pre-allocated RX ring buffer: a circular array of descriptors (typically 256 to 4,096 entries). Each descriptor points to a memory buffer where the NIC can deposit a frame.

If the ring fills up because software can't drain it fast enough, incoming packets are silently dropped at the NIC. No error to the sender. No log entry. The only trace is a bump in rx_missed_errors visible via ethtool -S.

3
Hardware Interrupt (IRQ)

After writing the frame to memory, the NIC fires a hardware interrupt to notify the CPU that new data is available. This is expensive: it forces a context switch, flushes caches, and disrupts whatever the CPU was doing.

Interrupt coalescing (ethtool -C) batches multiple packet arrivals into a single interrupt notification. Instead of one IRQ per packet, the NIC waits a configurable delay or packet count before firing. This trades a small amount of latency for a large reduction in interrupt overhead at high packet rates.

Context switch + cache flush per IRQ
4
softIRQ and NAPI Polling

Linux splits interrupt handling into two halves. The top half (hardIRQ handler) does minimal work: it disables further interrupts from the NIC, schedules a softIRQ (NET_RX_SOFTIRQ), and returns immediately. This must be fast because it blocks all other interrupts on that CPU core.

The bottom half (softIRQ context) is where real processing happens. NAPI (New API) polls the RX ring in a loop, processing a budget of 64 packets per poll call, up to 300 packets per softIRQ cycle. When the ring drains below a threshold, NAPI re-enables hardware interrupts and goes back to sleep.

If softIRQ processing takes too long or too many cycles are consumed, the kernel's ksoftirqd thread takes over. This is a regular kernel thread with lower scheduling priority, which means packet processing competes with other work on that core.

Budget: 64 pkts/poll, 300 pkts/softIRQ cycle
5
Driver RX Poll and sk_buff Allocation
NAPI poll callback (e.g. igb_poll)

The driver's NAPI poll function harvests packets from the RX ring and allocates a fresh sk_buff (socket buffer) structure for every single packet. This is the first major cost center in the entire path.

An sk_buff is approximately 240 bytes of metadata, allocated from the kernel's SLAB/SLUB allocator. At 1 million packets per second, the driver performs 2 million allocator operations per second (one alloc + one free per packet). Each allocation touches cache lines, contends on per-CPU freelists, and adds pressure to the memory subsystem.

03
L2
Layer 2: Core Network Stack

Protocol Processing

The sk_buff is now alive. The kernel routes it through the generic network stack: packet coalescing, CPU steering, IP validation, routing, and firewall hooks. Every packet, regardless of protocol, walks this path.

6
GRO (Generic Receive Offload)

GRO attempts to coalesce multiple small packets into larger ones before pushing them up the stack. This reduces the per-packet overhead for upper layers by amortizing header processing across several frames.

GRO is highly effective for TCP, where many sequential segments on the same flow can be merged. For UDP on Solana, the benefit is limited. Validator traffic consists of diverse, independent datagrams from many sources. GRO can group some flows (same 5-tuple) but the hit rate is low for typical gossip and shred traffic.

Low impact for varied UDP traffic
7
netif_receive_skb
Main entry into the network stack

This is the central dispatch function. It examines the EtherType field in the Ethernet header to determine which protocol handler should receive the packet. IPv4 packets go to ip_rcv(), IPv6 to ipv6_rcv(), ARP to arp_rcv().

Any packet-tap interfaces also hook in here. If tcpdump is running, every packet is copied to the tap socket at this point, even before any filtering. This is why running tcpdump on a busy validator adds measurable overhead.

8
RPS (Receive Packet Steering)

RPS is the software equivalent of hardware RSS (Receive Side Scaling). It hashes the packet's flow tuple (source IP, dest IP, source port, dest port, protocol) and uses the hash to steer the packet to a specific CPU core for processing.

Without RPS or RSS, all packets from a single NIC queue are processed on the same CPU core, creating a bottleneck. RPS spreads the load by re-queuing the sk_buff to another CPU via inter-processor interrupt (IPI). The IPI itself has overhead, but it's worthwhile when one core is saturated.

IPI cost per packet when steering across cores
9
IP Receive
ip_rcv() -> ip_rcv_finish()

The IP layer validates the packet header: version field, header checksum, TTL. It performs a routing table lookup to determine whether the packet is destined for a local socket, needs forwarding, or should be dropped.

The Netfilter PREROUTING hook runs here. Even if your iptables rules are empty, the kernel still traverses the hook chain to check. If IP fragmentation reassembly is needed, it happens at this stage too. Fragmentation is rare for Solana traffic since shreds are sized to fit a single datagram.

10
Local Delivery
ip_local_deliver() -> ip_local_deliver_finish()

After the routing decision confirms this packet is destined for a local socket, ip_local_deliver() runs. The Netfilter LOCAL_IN hook fires here. This is where your iptables INPUT rules execute.

Even empty iptables rules mean traversing hook chains per packet. If connection tracking (conntrack) is loaded, the kernel allocates per-flow tracking structures at this point. For a validator receiving traffic from thousands of unique sources, conntrack can become a significant memory and CPU consumer.

Netfilter hooks + conntrack per packet
04
L3
Layer 3: UDP Socket Layer

Socket Lookup and Queueing

The packet has survived IP processing and Netfilter. Now the kernel must find the right socket and park the packet in its receive queue. Two steps, but both carry hidden contention points.

11
UDP Receive and Socket Lookup
udp_rcv() / __udp4_lib_rcv()

The UDP layer looks up the destination socket in a hash table keyed by (destination IP + destination port). For a validator with a handful of listening sockets, this lookup is fast. The kernel also performs UDP checksum verification at this stage unless the NIC already offloaded it.

If early demux is enabled (it usually is), the kernel tries to cache the socket lookup result from a previous packet in the same flow, skipping the hash table search. BPF socket filters, if attached, execute here as well.

12
Socket Receive Queue
udp_queue_rcv_skb() -> sock_queue_rcv_skb()

The sk_buff is appended to the socket's receive queue. This queue is a linked list of sk_buff structures, and appending to it requires holding a spinlock. Under high packet rates with multiple CPU cores delivering to the same socket, this lock becomes a contention point.

Buffer accounting checks sk_rmem_alloc against sk_rcvbuf. If the socket buffer is full, the packet is silently dropped. No backpressure signal is sent to the sender. No error returned to the application. The kernel simply frees the sk_buff and increments a drop counter. At validator packet rates, this is the most common reason for packet loss.

05
L4
Layer 4: Userspace Boundary

The Final Copy

The packet is sitting in the socket queue, waiting. The Agave validator's streamer thread calls a system call to pull it across the kernel-to-userspace boundary. This last step is deceptively expensive.

13
recvmsg and recvmmsg
udp_recvmsg() -> copy_to_user()

The application calls recvmsg() (one packet at a time) or recvmmsg() (batch of packets in one syscall). Each call is a system call: user-to-kernel context switch. On Spectre-mitigated kernels, this adds approximately 100-200ns per syscall for the indirect branch prediction barriers.

Inside the kernel, udp_recvmsg() dequeues the sk_buff from the socket's receive queue and calls copy_to_user() to copy the payload data into the application's buffer. This is a real memcpy operation. At 1M packets per second with 1,232-byte payloads (Turbine shred size), that's roughly 1.2 GB/s of pure memory copy.

After the copy, the sk_buff is freed. This isn't a simple kfree(). The destructor callbacks run (socket buffer accounting updates, memory charge adjustments), and the 240-byte struct returns to the SLAB allocator. One more allocator operation per packet.

06

What This Path Gives You

The classic kernel networking path exists for good reason. These 13 steps buy three properties that matter for debugging, security, and compatibility. The next part of this series explains exactly where those properties start costing more than they're worth at validator packet rates.

General

Works with any NIC from any vendor. No driver-specific code paths. No hardware dependencies. Plug in a NIC, load the driver, and this path works.

Compatible

tcpdump, iptables, ss, netstat all work. Every standard Linux networking tool integrates with this path because it goes through all the standard hooks.

Observable

BPF, ftrace, and perf can trace every step. You can instrument any function in the path, count packets at any layer, and measure latency between any two points.

Looking Ahead

General. Compatible. Observable. These are real advantages. But at validator packet rates, the cost of maintaining these properties through 13 steps of per-packet processing becomes the bottleneck itself. Part 3 measures exactly where and how much.
