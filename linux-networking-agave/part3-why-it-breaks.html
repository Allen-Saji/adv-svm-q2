Part 3 of 7 Linux Networking for Agave Validators
Part 3

Why The Classic Path Breaks

You know the 15-step packet journey from NIC to userspace. Now consider what happens when every one of those steps runs a million times per second. The math is not kind.

01

One Million Packets Per Second

In Part 2, we traced a single Solana packet through 15 kernel steps: NIC DMA, interrupt, NAPI poll, sk_buff allocation, protocol demux, netfilter, checksum, socket lookup, queue insertion, wakeup, recvmsg, userspace copy. Each step is cheap in isolation. A few hundred nanoseconds here, a microsecond there.

At low traffic, nobody notices. But Solana validators routinely handle 800K to 1.5M UDP packets per second during normal operation: turbine shreds, repair requests, votes, gossip, QUIC-wrapped transactions. Scale any per-packet cost by a million and the seconds fill up fast.

Every bar above is a step that costs CPU time per packet. We can group these 15 steps into six cost centers where the time actually goes. Let's put real numbers on each one.

02

The Six Cost Centers

These estimates use measured values from kernel profiling literature and typical validator hardware (AMD EPYC / Intel Xeon, DDR5, ConnectX-6 / Intel E810 NICs). Ranges reflect variance across hardware and kernel configuration.

Cost Center A
sk_buff Lifecycle
One alloc + one free per packet
100-200ms/s

Every packet that enters the kernel gets an sk_buff struct: the kernel's universal packet metadata container. That's roughly 240 bytes from the SLAB allocator per packet. At 1M pps, that's 2 million allocator round-trips per second.

~240B per sk_buff
2M alloc ops/sec
50-100ns per alloc
  • Each allocation hits the SLAB/SLUB per-CPU cache or falls back to the per-node partial list. Cache misses here are expensive.
  • free_skb() is not a simple kfree(). It runs destructor callbacks, releases fragment pages, and updates socket memory accounting.
  • Under pressure the allocator contends on per-node locks, adding 100+ ns to every operation.
Cost Center B
Memory Traffic
Cache-line misses and payload copies
300-500ms/s

This is the single largest cost. Each packet touches at least four memory locations: the DMA ring buffer, the sk_buff struct (spanning ~4 cache lines), the socket queue pointers, and the final userspace buffer. Each L3/DRAM cache-line miss costs 60-100ns.

8-12 cache lines / metadata
1232B = 20 cache lines / payload
~20M cache writes/sec
  • The copy_to_user() call writes 1,232 bytes (Solana's MTU) into userspace memory. That's 20 cache lines written per packet, 20M writes per second at 1M pps.
  • DMA buffer to sk_buff data pointer is a reference, not a copy. But the sk_buff metadata itself is freshly allocated and almost always cold in cache.
  • NUMA-aware allocation helps, but cross-socket memory access (when IRQ affinity doesn't match the receiving thread's CPU) pushes latency to 150ns+ per line.
Cost Center C
Netfilter Hooks
Firewall traversal per packet
50-100ms/s

Even with an empty iptables ruleset, the kernel still traverses the netfilter hook registration chain for every packet. With rules, it's O(n) per rule per packet. Connection tracking (conntrack) allocates a per-flow hash entry and maintains state.

O(n) per rule
conntrack hash alloc
  • Production validators often have firewall rules for rate-limiting, geo-blocking, and port filtering. Each rule is a branch per packet.
  • conntrack maintains a hash table of active flows. For UDP (stateless transport), this is pure overhead: the kernel tracks state that the protocol doesn't need.
  • Disabling conntrack for validator traffic is a common optimization, but doesn't eliminate the hook traversal cost.
Cost Center D
Socket Mechanics
Hash lookup, queue locks, buffer pressure, wakeups
100-200ms/s

Every packet needs a socket lookup (~100ns hash table probe), then insertion into sk_receive_queue under a spinlock. Under contention with multiple cores, that lock costs 200-1000ns per acquisition.

~100ns hash lookup
200-1000ns spinlock
  • Silent drops: if sk_rmem_alloc exceeds sk_rcvbuf, the packet is dropped. No error to the sender, no backpressure signal. You only see it in the UDPInErrors counter.
  • sock_def_readable() triggers wake_up_interruptible(), which involves the scheduler. If the receiving thread is sleeping on recvmsg, waking it pollutes the cache of whatever core it lands on.
  • Multiple softIRQ contexts competing to queue packets on the same socket creates lock convoy effects.
Cost Center E
Checksums
Software checksum unless hardware offload
~100ms or ~0

The UDP checksum covers the pseudo-header + UDP header + payload. Without NIC offload, the CPU reads every byte of each 1,232-byte packet. At 1M pps: 1.2 GB/s of reads just for checksumming.

1232B read per packet
1.2 GB/s without offload
  • Most validator-grade NICs (Mellanox ConnectX-6, Intel E810) support hardware checksum offload. With offload enabled, this cost drops to near zero.
  • Without offload (misconfigured NIC, or software-based virtio in a VM), this becomes a significant CPU consumer. Always verify offload is active with ethtool -k.
  • The kernel can also use CHECKSUM_UNNECESSARY to skip re-verification when the NIC has already validated.
Cost Center F
Scheduling Overhead
IRQs, softIRQs, syscalls, context switches
100-200ms/s

The orchestration tax. Every packet delivery involves multiple privilege transitions and scheduling decisions that consume CPU independently of the packet itself.

1-2us IRQ entry/exit
100-200ns Spectre syscall
  • IRQ entry/exit: save/restore registers, acknowledge the interrupt controller, potentially cross-CPU IPI for interrupt steering. 1-2 microseconds per interrupt.
  • softIRQ scheduling: ksoftirqd context switches when softIRQ budget is exhausted, polluting TLB and instruction cache.
  • Spectre-mitigated syscalls: post-Spectre, every recvmsg syscall includes IBPB/STIBP barriers. That's 100-200ns of pure mitigation overhead per call.
  • Thread wakeup: when the receiving thread sleeps on recvmsg, waking it triggers scheduler runqueue insertion and potential cross-core migration. The newly-woken thread starts with a cold instruction cache.

The Problem

That's 75-120% of a single CPU core consumed by packet reception alone. Before Agave does anything useful: QUIC decryption, signature verification, deduplication, banking stage, proof-of-history. The kernel's packet path is eating the CPU budget that the validator needs for actual consensus work.

04

The Band-Aid: Batched UDP

The kernel provides one optimization within its existing rules: recvmmsg() and sendmmsg(). Instead of one packet per syscall, you receive up to N packets in a single kernel round-trip.

Agave uses batch sizes of 128 to 512 packets, mapping directly to its internal PacketBatch structure. The syscall reduction is dramatic:

Key Insight

recvmmsg is "optimized classic UDP." It's the local maximum within the kernel's existing rules. Only one line in that table turns green. The other six costs, totaling 800+ ms per second, remain untouched. To make a real dent, you need to change which rules apply, not optimize within them.

05

The Ceiling

We've exhausted what the traditional kernel packet path can offer. Even with recvmmsg batching, hardware checksum offload, conntrack disabled, and IRQ affinity tuned, the fundamental architecture remains: allocate per packet, copy per packet, lock per packet, traverse hooks per packet.
